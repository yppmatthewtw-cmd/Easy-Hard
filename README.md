# EasyHardMoney NDX — 三引擎整合檔 (A ∩ B ∩ C)

把三個獨立的 EASY/HARD MONEY 判區引擎合併成單一 Excel 檔,並在其中新增一個「三方交集」的整合判區。

## 交付檔案

`EasyHardMoney_NDX_2026R4.5.3_COMBINED_ABC.xlsx`

## 整合規則

| 條件 | 整合判區 |
|---|---|
| A、B、C 三個引擎同日**全部** EASY | `EASY` |
| A、B、C 三個引擎同日**全部** HARD | `HARD` |
| 其餘所有情況(任一引擎分歧) | `UNCERTAIN` |

## 來源引擎

| 代號 | 原始檔 | 判區欄 | 分數欄 | 判區門檻 |
|---|---|---|---|---|
| A | `AFable_ EasyHardMoney … 2026R4.5.3_2.xlsx` | `02A_每日分段!Y` | `AX` (18 項加權) | ≥70 EASY / >40 UNCERTAIN / 其餘 HARD |
| B | `B5.6_Sol_ EasyHardMoney … 2026R4.5_SOL_CodexReviewed.xlsx` | `02A_每日分段!R` | `Q` (5 項加權) | ≥92 EASY / ≥45 UNCERTAIN / 其餘 HARD |
| C | `CGrok_ EasyHardMoney … 2026R4.5.3_GROK.xlsx` | `02A_每日分段!AH` | `AG` (18 項加權) | ≥80 EASY / ≥40 UNCERTAIN / 其餘 HARD |

三個引擎的指標數與門檻都不同,這是整合後 EASY/HARD 大幅收窄的直接原因。

## 工作表結構(共 27 張)

**整合表(新增,置於檔首)**

## 資料範圍與結果

涵蓋 2016-07-08 至 2026-07-10,共 2,515 個交易日,三個檔案逐列同日對齊(主表 P 欄逐日活算核對)。

| 判區 | 整合 (A∩B∩C) | A 引擎 | B 引擎 | C 引擎 |
|---|---|---|---|---|
| EASY | 394 (15.7%) | 1,757 | 499 | 702 |
| UNCERTAIN | 1,848 (73.5%) | 441 | 1,424 | 1,343 |
| HARD | 273 (10.9%) | 317 | 592 | 470 |

兩兩判區一致度:A-B 1,013 日 (40.3%)、A-C 1,226 日 (48.7%)、B-C 1,862 日 (74.0%);三方完全一致 808 日 (32.1%)。

最長整合 HARD 區間為 2022-09-13 至 2022-11-10 共 43 個交易日;最長整合 EASY 區間為 11 個交易日(2017-05、2019-12、2020-01、2020-02、2021-06 各一段)。

## 實作說明

- 四張整合表(01/05/06/07)全部為活公式,不含寫死結果。整合判區由 `=IF(EASY票數=3,"EASY",IF(HARD票數=3,"HARD","UNCERTAIN"))` 得出,票數再引用 `A_`/`B_`/`C_` 原表的判區儲存格。
- **哪些來源會連動**:A 原檔帶 65,479 條活公式、B 原檔帶 23,634 條,改動它們的輸入格會一路更新到整合判區。但 C 原檔本身就只有數值、沒有任何公式(0 條),所以 C 判區欄是資料而非公式 — 要改 C 的判區須直接編輯 `C_02A_每日分段` 的 AH 欄。
- `07_整合區間` 的列數不寫死:表格備有 400 列容量,實際顯示幾段由 N2(`=MAX(區間編號)`)活算決定,多餘列自動留白;若來源改動後段數超出容量,N3 會顯示警告。區間報酬給兩個定義:`期內報酬%`(首收→末收,判區成立後才進場的報酬,單日區間必為 0%)與 `含首日報酬%`(前收→末收,含觸發判區當日的跳空)。
- 配色:表頭深藍 `1F4E79`、EASY 綠 `C6EFCE`、UNCERTAIN 黃 `FFEB9C`、HARD 紅 `FFC7CE`。三個來源檔本身對 UNCERTAIN 的黃色並不一致(B 與 C 用 `FFEB9C`,A 自己的 Y 欄用較深的 `FFE699`),整合表採用三取二的 `FFEB9C`,各來源原表則一律保留其原有顏色不動。字型沿用原檔(Arial 為主)。
- 五張整合表都設好了列印版面(長表橫向、縮放至一頁寬、第 4 列表頭逐頁重複),與原檔 A 各表的既有設定一致。
- 只使用 Excel 2007 以前就存在的函數(`IF` `COUNTIF` `COUNTIFS` `INDEX` `MATCH` `SUMPRODUCT` `MAX` `MIN` `TEXT`),確保跨版本可算。數字開頭的表名(如 `01_整合判區`)在全部 138,627 個跨表引用中都有加單引號,這是 Excel 解析的必要條件。
- 已設定開檔全表重算,任何 Excel 版本開啟時都會重新計算所有快取值。

## 重算狀態

全檔 137,238 條公式已完整算出並寫入快取值,**零公式錯誤**。

重算流程刻意分兩步:先複製一份給 LibreOffice 計算,再把算出的值注入回 openpyxl 建置的原檔。原因是讓 LibreOffice 直接覆寫交付檔會破壞它 —— 會把找不到的字型改名成本機才有的 `WenQuanYi Zen Hei`、把 138,627 個跨表引用的單引號全部拿掉(數字開頭的表名因此無法被 Excel 解析)、把浮點數重新序列化成 15 位有效數字,並更動個別數字格式與列高。注入法讓交付檔同時具備正確的計算值與逐位元保真的原始格式。

重算工具會另外標示 `B_10_審查與修訂紀錄` 的 43 個儲存格,那是誤判:該表是 B 原檔自己的審查紀錄,說明文字裡本來就引用了錯誤代碼(例如「公式仍引用已刪除的 02_每週分段,顯示 #NAME?。」、「0 個 #REF!/#DIV/0!/#VALUE!/#NAME?/#N/A/#NUM!」)。這 43 格全部是文字格(`data_type='s'`),與原檔 B 逐字相同,該表在原檔與整合檔中都是 0 條活公式。

## 承襲自原檔的已知小問題

`A_01_指標庫` 的 H20/H21(T4=6、T5=26 兩項權重)在來源檔 A 中就是以**文字**而非數字儲存(權重合計仍為 100)。此處按原樣保留未作更動;Excel 運算時會自動轉型,算出的結果與原檔一致,但日後若要改動該權重表,建議一併改回數值格式。

## 建置與驗證腳本

`scripts/build_combined.py` 產生整合檔;`scripts/verify_combined.py` 從**未經修改的原始上傳檔**獨立重新推導整合結果,再逐格比對交付檔,涵蓋整合規則、原檔資料保真、日期對齊、公式錯誤與各摘要表數字。
